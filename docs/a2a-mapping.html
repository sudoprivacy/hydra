1. Identity — persistent NAME + per-run PID (BOTH, not either/or)

Hydra (sessionManager.ts) and nexus (rust/kernel/src/core/agents/registry.rs, the "per-PID agent SSOT / task_struct analogue") model identity the SAME way — a stable identity plus an ephemeral per-run handle. nexus's AgentDescriptor carries both name and pid.

Hydra CopilotsessionName(per start)tmux pane pid
nexus AgentRegistryAgentDescriptor.name → /agents/{name}/chat-with-me (wal, replicated)AgentDescriptor.pid = the OS host_pid (+ .local_id when micro-agents share a process) → /proc/{pid}/chat-with-me (DT_PIPE, node-local); generation bumps on reconnect— the pid is the OS pid; no separate field
Resolved (owner "pid" thread — nexus-vfs #195): the two mailbox surfaces are complementary — §3.5 persistent NAME mailbox /agents/{name}/chat-with-me (durable, cross-machine A2A address) AND §3.6 per-run PID /proc/{pid}/chat-with-me (node-local pipe for the live run); it's both. And the pid IS the OS host_pid (contracts::agent_pid → "{host_pid}[.{local_id}]"): so /proc, ps, kill, gdb align and the mapping needs no lookup, and there is no separate host_pid field (SSOT — it IS the pid). Lifetime = the OS process's (reuse is fine: durable refs are the NAME or timestamped logs, so no start_time needed). local_id is a runtime per-process counter (cross-platform, incl. coroutines/threads), not an OS thread id. Hydra reports a run's pane pid as the host_pid, so the nexus pid == the pane's OS pid; hydra's own lifecycleEpoch stays its internal fencing token.

3. Cross-node uniqueness & §F naming OPEN — implement next

Identity flow (the "original nexus design", owner Q7): auth mint agent --subject-id <name> → AuthKeyRecord{subject_type:Agent, subject_id:<name>} (per-node SOLO store, HMAC-keyed) → the sk- key resolves so OperationContext.agent_id = subject_id → MailboxStampingHook stamps from = agent_id, overwriting any caller value (unforgeable), and fail-closes an unauthenticated A2A write. So from == the minted name.

  • Within-node uniqueness: enforced (find_active_subject, nexus-vfs #175).
  • Cross-node uniqueness: an UNENFORCED naming convention today. The name is subject_id, supplied verbatim at mint — node_id is NOT folded into it. node_id (read_or_mint_node_id, opaque u64 at <data_dir>/.node_id) is used only for raft identity (cert SAN node/{id}); it is not VFS-exposed, so an agent can't even read its own node_id today. The §F default-name generator ({node_id}.{worktree}) is NOT implemented anywhere — only referenced in comments.
Task §F (owner: prioritize): land node-anchored default naming so cross-node uniqueness holds by construction, not discipline. Two parts: (a) expose the local node_id to frontends (a small read-only VFS/procfs surface, or a mint helper), and (b) generate the default name <node_id>.<worktree/context> at mint. Design fork to settle: do (b) in the nexus mint (auto-anchor a default) or in the frontend (hydra/sudocode-host, which knows the worktree)? Recommend: nexus exposes node_id + a mint auto-anchor mode; frontend supplies the worktree suffix. This is the load-bearing cross-node mechanism. Coordination: a parallel effort (feat/agent-signed-authorship) is landing agent identity certs nexus://agent/{name} — the from-unforgeable upgrade from kernel-stamp → cryptographically signed authorship — and is editing mint.rs, where §F's default-name lives, and the name feeds that cert's SAN. So §F rides WITH that work, not independently. Once it lands, §3/the identity flow above becomes cert-signed (not just kernel-stamped).

4. tmux & visibility DECIDED — drop tmux for messaging

  • Mailbox = durable/ordered/replicated/audited DT_STREAM — strictly MORE visible than ephemeral node-local tmux scrollback. cat/tail -f via mount; (later) Matrix room. Full visibility without tmux or Matrix.
  • tmux occupies stdio 0/1 and contends with the user — removed for the message plane.
  • tmux's remaining role (process host/TTY) is orchestration; hydra keeps it via register_external (report the run in, don't hand spawning to nexus).

6. Broadcast / multicast DECIDED — native stream fan-out

Owner Q6 — confirmed against the kernel:

  • DT_STREAM is natively multi-reader / fan-out. Reads are non-destructive + offset-based (each reader its own cursor); sys_watch wakes ALL parked watchers of a path (notify_all), and the raft stream-wakeup observer wakes watchers on every replica — genuine 1→N, cross-node. Proven by a2a_wakeup.
  • So broadcast = ONE shared stream (e.g. /agents/<copilot>/broadcast/chat-with-me) that N workers watch. No new kernel primitive.
  • DT_LINK is NOT the fan-out tool. It's a one-hop symlink (many→ONE target, self-loop-rejected). It can ALIAS each worker's path to the shared stream (addressing convenience / fan-IN), but the multicast comes from the stream's multi-reader property, not the link. No primitive clones one write into N per-agent streams.
