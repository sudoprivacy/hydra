3. Cross-node name uniqueness DECIDED

The collision worry (two machines' Worker#1) — the model has two halves (project_agent_identity_model):

  • Within-node: ENFORCED (landed, nexus-vfs #175). mint_key refuses a subject that already holds an active key (CAS scan of the local store).
  • Cross-node: uniqueness is BY the node-anchored NAME — {node_id-anchor}.{...} makes names disjoint across nodes by construction. Each node has a persistent node_id (read_or_mint_node_id, already in the cert SAN). The auth store is per-node SOLO (never federated), so this naming is load-bearing, not cosmetic.
The AUTO node-anchoring is design-locked but its default-name generator is deferred to sudocode-host §F (not yet landed). So hydra supplies the anchor itself — <node_id>-hydra-w<workerId> — which IS the load-bearing mechanism. hydra reads the local node_id from the daemon identity. No collision hole; not blocked on §F.

4. tmux & visibility DECIDED — drop tmux for the message plane

tmux was chosen last year for visibility (messages visible in the pane; files felt invisible). That was a forced choice under insufficient infra. It no longer holds:

  • The mailbox is a durable, ordered, replicated, audited DT_STREAM — strictly MORE visible than tmux scrollback (which is ephemeral, node-local, lost on restart). collect/read any time, any node.
  • Surfaces for humans/agents to SEE it: FUSE/WinFsp mount → cat / tail -f; (later) the Matrix adapter → a chat room. Full visibility without Matrix, and without tmux.
  • tmux occupies stdio 0/1 and contends with the user — a real cost the mailbox removes.

tmux's remaining role (agent process host + TTY) is an orchestration concern (hydra's, §8.1), separable from messaging. Recommendation: drop tmux for messaging now; revisit the process-host model separately (an agent could read its mailbox via the mount instead of a shared TTY).

5. The switchable messaging abstraction DECIDED — the core seam

hydra has users; the migration must not be heavy-handed. So the WHOLE message plane goes through one hydra abstraction with swappable backends — a true one-switch cutover:

Backendsend / broadcastworker→copilot attentionwatch / read
Legacy (default, today)tmux keystroke injectNotificationStore jsonfs.watchFile / EventHub poll
A2A (nexus)write peer mailboxwrite copilot mailboxsys_watch + collect
Dual (migration)writes both (equivalent to double-write) — flip readers to A2A once trusted, then drop Legacy
  • Mirrors hydra's existing HydraTransport backend pattern (in-process now; add a2a alongside, config-switchable).
  • Control/message-plane split: control (create/stop/git/logs) stays on the existing transport; only the message-plane ops (sendMessage, broadcastToWorkers, events, notifications) route through the messaging abstraction.
  • Because switchable + equivalent, Dual = double-write for free — no separate migration mechanism.
